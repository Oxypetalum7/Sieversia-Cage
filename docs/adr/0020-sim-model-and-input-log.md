# ADR-0020: Sim は 1 日ずつ進む純粋な関数とし、入力（水やりの記録）を DB に残す

- ステータス: 採択
- 日付: 2026-10-29
- 関連: ADR-0011（アルバムの正は成長データ）, ADR-0014（水やりの反応と記録）, ADR-0015（`:core:sim` は純 Kotlin）, ADR-0018（アルバムの正のデータは Room 3）, ADR-0019（M2 の計画）, docs/spikes/README.md（M2-1 結果）

## 背景

M2-4 で Sim を本実装する。発注書は「パラメトリックな簡易モデル（経過日数・水やり・季節係数から枝ぶりと花の状態を決める）」とし、本格的なシミュレーションへの差し替えの余地を残すことを求めている。成長段階は「芽 → 葉 → 蕾 → 開花 → 綿毛（回転）」。

今のスパイクの Sim は `simulate(ageDays)` で、経過日数のしきい値だけで段階を決めている。

あわせて、ADR-0018 と ADR-0019 で保留にした次の 2 点を決める。

- **アルバムに何を保存するか**: ADR-0018 では Sim の出力だけを保存する。出力に項目を足すと、それより前に記録した日にはその値がなく、マイグレーションの仮の値で描かれる
- **水やりの数え方**: ADR-0014 で「連打の扱い、1 日の上限などは Sim の本実装で決める」とした。M2-1 で、連打はすべてアプリに届くことがわかった

遊び方として、次のことを決めた（2026-10-29、ユーザーと相談）。

- 毎日水をやれば、約 3 週間で芽生えから綿毛まで育つ
- 綿毛のあとは、同じ株が花と綿毛を繰り返す（チングルマは実際に多年生の小低木）。株は周を重ねるごとに少しずつ大きくなる
- 水やりを忘れても枯れない。育ちが遅くなるだけで、水をやれば元に戻る。土が乾いていく表現を入れたい
- 季節係数は控えめに効かせる（実際の月で 0.8〜1.2 倍）。冬に始めてもちゃんと育つ

## 検討した選択肢

### Sim の形

1. **経過日数から直接決める**（今のスパイクの形）— 単純だが、水やりや季節のように日ごとに変わる入力を積み重ねられない
2. **1 日ずつ進む純粋な関数**（`step(昨日までの状態, その日の入力) → 今日の状態`）— 植えた日から入力を順に当てはめれば、いつの状態でも求め直せる。日ごとの入力を自然に積み重ねられる
3. **状態を DB に持ち、毎日書き換える** — 求め直せず、Sim を差し替えたときに過去の入力から作り直せない

### Sim の入力をどう残すか

1. **残さない（出力だけ）** — ADR-0018 のまま。出力に項目を足すと、過去の日は仮の値になる
2. **水やりの記録（日付ごとのタップ数）を DB に残す** — ADR-0014 の「記録は後追い」のために、どのみち必要になる。植えた日と日付があれば季節も決まるので、Sim の入力は全部ここから求め直せる
3. **アルバムの各日に入力の写しも持つ** — 2 と同じ情報を二重に持つことになる

## 決定

### Sim の形: 1 日ずつ進む純粋な関数（選択肢2）

- `:core:sim` に `step(state: PlantState, input: DayInput): PlantState` を置く。純 Kotlin のまま（ADR-0015）で、日付は `java.time.LocalDate` を使う
- 今日の状態は、植えた日の初期状態から、昨日までの各日の入力を順に `step` に当てはめて求める
- **入力（`DayInput`）**: 日付、その日の水やりのタップ数
- **出力（`PlantState`）**: 次の項目を持つ。見た目と状態の欄の文字は、これだけを見て作る（今までどおり Compiler は Sim の出力だけを見る）
  - 成長段階（芽 / 葉 / 蕾 / 開花 / 綿毛）と、段階の中での進み具合（0〜1）
  - 周回数（最初の一生が 0。綿毛のあと葉の時期に戻るたびに 1 増える）
  - 枝ぶり（枝の数など）と花の数。周を重ねるごとに増え、上限がある
  - 土の湿り気（0〜1）と元気さ（0〜1）
  - 植えてからの経過日数

### 成長の仕組み

- 毎日「成長ポイント」を積み上げ、段階はポイントで進む（日数では進まない）
- その日の成長ポイント = 基本の量 × 元気さの係数 × 季節係数
- **水やり**: その日に 1 回以上タップすれば「水をやった日」と数える。何回連打しても 1 回と同じ。生のタップ数は記録に残す
- **土の湿り気**: 水をやった日は 1.0。やらない日が続くと 1 日ずつ減り、3 日ほどで乾ききる
- **元気さ**: 土の湿り気を追いかけて変わる。乾いても 0 にはならず、成長が止まりかけるだけで枯れない
- **季節係数**: 実際の月から決め、0.8〜1.2 倍（夏に高く、冬に低い）
- **繰り返し**: 最初の一生は「芽 → 葉 → 蕾 → 開花 → 綿毛」を約 3 週間で進む。そのあとは「葉の時期 → 蕾 → 開花 → 綿毛」を約 2 週間ごとに繰り返す
- 具体的な数値（基本の量、しきい値、減り方）は実装とテストで決め、ここには書かない

### 日の区切り

- 端末の現地時刻の日付で区切る
- その日の水やりが効くのは翌日の成長から。タップしたその場では、ドキュメントの中の跳ねる反応だけが出る（ADR-0014）
- 毎日の tick が遅れたり抜けたりしても、次に Sim を進めるとき（tick かアプリの起動時）に、抜けている日を順にまとめて進める

### 入力の保存: 水やりの記録を DB に残す（選択肢2）

- Room の DB（ADR-0018）に、次の表を足す。DB の版を 2 に上げ、最初のマイグレーションとそのテスト（`MigrationTestHelper`）を書く
  - `watering_log`: 日付（主キー）とその日のタップ数
  - 植えた日（株の情報）
- アルバム（`album_entry`）には、今どおり Sim の出力を保存する。出力の項目が増えるので列を足す
- これで、アルバムは「Sim の出力（当時の育ち方）」、`watering_log` と植えた日は「Sim の入力」を正のデータとして持つ。ADR-0018 の時点で候補に挙がった「両方」の形になる
- **出力に項目を足したときの埋め直し**: 過去の日の新しい列は、入力から Sim を回して求める。既存の列（当時の育ち方）は書き換えない

### 決めないこと

- **水やりの通知**（土が乾いたときに知らせる）: 発注書の MVP の範囲にない新しい機能なので、ここでは候補として書くだけにする。毎日の tick（M2-5）で土が乾いたかがわかるので、そこで通知の許可（`POST_NOTIFICATIONS`）や時間帯を含めて、別の ADR で決める
- **土が乾いていく見た目**: M3 で作り込む。M2 では出力の値として持つところまで

## 理由

- **求め直せる**: 入力を残し、Sim を純粋な関数にしておけば、いつの状態でも植えた日から求め直せる。テストも入力を並べるだけで書ける
- **差し替えの余地**: 発注書の「オーキシン創発級の Sim への差し替え」も、同じ入力から別の `step` を回すだけで試せる
- **入力の記録は二重にならない**: 水やりの記録は ADR-0014 のためにどのみち必要で、Sim の入力はそれと植えた日だけで足りる
- **過去の育ち方は守る**: アルバムの既存の列は当時の出力のまま残し、ADR-0011 の「育ち方が正しく残ることを優先する」を保つ。新しい列だけを入力から埋めるので、新しい表現も過去の日に届く
- **連打を 1 回と数える**: タップの回数を競う遊びにしない。ホーム画面で「毎日気にかける」ことが体験の核なので、日ごとに水をやったかどうかで数える

## 影響

- `PlantState` が大きくなり、`simulate(ageDays)` は `step` を植えた日から回す形に置き換わる。Compiler と `:core:data` の呼び出し側も合わせて直す
- DB の版を 2 に上げる。最初のマイグレーションなので、`MigrationTestHelper` のテストを実機で回す（ADR-0018）
- 水やりのタップ（M2-1 の `WateringReceiver` とアプリ内の `onAction`）を `watering_log` に記録する
- 毎日の tick（M2-5）は、「抜けている日を進める → アルバムに記録 → ウィジェットを更新」になる
- 植えた日から毎回すべての日を回すと、日が増えるほど時間がかかる。数年分でも数千回の単純な計算なので当面は問題にしないが、遅くなったら途中の状態を保存して続きから回す
