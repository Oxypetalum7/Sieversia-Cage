# ADR-0002: スパイクを本リポジトリ内でモジュール分割して行う

- ステータス: 採択
- 日付: 2026-10-03
- 関連: ADR-0001, 発注書「アーキテクチャ」「初日スパイク」

## 背景

本実装の前に初日スパイク（アプリ内再生 / ランチャー対応 / 式アニメーション / ドキュメント保存・再読込）で構想の背骨を検証する。スパイクのコードをどこに置くかを決める必要がある。

## 検討した選択肢

1. **使い捨ての別リポジトリでスパイク** — 本体を汚さず自由に試せるが、知見を本体へ移植する手間が発生し、捨てたコードと本体の構成がずれる
2. **本リポジトリで単一モジュールのままスパイク** — 立ち上げは最速だが、後からSim/Compiler/Surfaceを分割するリファクタが必要になる
3. **本リポジトリで最初から三層に対応するモジュールを切ってスパイク** — 初期設定はやや重いが、スパイクがそのまま骨組みになる

## 決定

選択肢3。以下の構成で開始する。

```
:sim        純Kotlin（JVMモジュール。将来のKMP化を見据え Android 依存を持たない）
:compiler   Sim状態 → RemoteCompose ドキュメント
:app        ショーケース / アルバム / ウィジェット（Surface群）
```

## 理由

- 発注書の核である「Sim と Surface はドキュメントだけを介して繋がる」分離を、モジュール境界（依存方向）でスパイク初日から強制できる
- スパイクで書いたコードが捨てられず骨組みとして残る
- Phase 2（Compiler層のサーバー生成化）・退路（Surface主役交代）・Sim層KMP化のいずれも、モジュール単位の差し替えで成立する

## 影響

- スパイク段階からGradleのマルチモジュール設定が必要
- スパイク中の試行錯誤コードが履歴に残る（必要ならスパイク完了時に整理する）
- `:sim` に Android 依存を持ち込まないことを継続的に守る必要がある
